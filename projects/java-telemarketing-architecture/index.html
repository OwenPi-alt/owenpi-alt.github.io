CASE 04 / ENGINEERING IN DETAIL

电销系统架构改造

当时既要拆分服务，也要处理锁竞争、超时和 OOM。

奇富科技 · 开发 Leader · 2018.04 — 2026.03

问题与约束

人工和机器人外呼业务持续迭代，原单体系统出现锁竞争、超时和 OOM。改造需要同时面对服务边界、下游调用和数据访问问题：既要为后续业务留出扩展空间，也要处理当前运行中的具体压力点，并协调任务调度、配置和团队交付。

核心链路简化示意

以下图示为技术思路的简化表达。

  1. 01 / 业务受理人工与机器人外呼
  2. 02 / 规则校验禁呼、黑名单与限制
  3. 03 / 服务协作业务调用与任务管理
  4. 04 / 数据支撑缓存、查询与冷热分离

架构取舍与实现

01

按业务职责推进服务拆分

难点单体中多类职责相互影响，局部压力容易变成整体运行问题。

方案主导单体向微服务拆分，并引入 XXL-JOB 与 Apollo 管理任务和配置。当前系统设有独立外呼校验服务，处理禁呼、黑名单、号码与次数限制。

价值让关键规则与业务执行形成清晰边界，使问题定位和后续变更有明确落点。

02

控制并行调用的资源边界

难点坐席标签依赖多个下游查询，串行等待与单项失败都会影响结果整理。

方案标签查询采用有界线程池和 CompletableFuture 并行获取下游结果；单项异常时，继续整理已有信息。

价值在利用并行能力的同时限制资源使用，并保留部分结果处理路径，避免把所有依赖绑成同一成败。

03

把性能治理落到具体访问路径

难点锁竞争、慢查询和内存压力交织，单一参数调整难以覆盖所有问题。

方案围绕并发访问调整 JVM 参数，优化 SQL 索引与 Redis 缓存，并进行冷热数据分离，分别处理运行时、查询和数据规模问题。

价值让每项治理动作对应具体压力来源，便于比较改动效果并观察新的瓶颈。

工程价值

把架构演进与具体稳定性问题连接起来，让系统改造既有清晰边界，也有可验证的实施抓手。

验证关注点

  • 服务拆分前后的规则、异常返回和业务限制是否保持一致？
  • 下游慢响应或单项失败时，线程资源与部分结果处理是否符合预期？
  • JVM、SQL、缓存和冷热分离的调整，是否在可比较负载下验证？

我的职责

主导单体向微服务拆分，承担技术方案、核心开发和团队交付，协同产品、测试与运维处理迭代和线上问题。

技术与主题

  • 微服务

  • JVM
  • MySQL / Redis
