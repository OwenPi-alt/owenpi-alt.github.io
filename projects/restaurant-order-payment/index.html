CASE 01 / ENGINEERING IN DETAIL

餐饮订单与支付系统

通知发出去了，门店有没有收到，还得分开看。

百味云 · 资深软件工程师 / 技术组长 · 2016.10 — 2018.04

问题与约束

云小二、云掌柜连接餐饮经营中的订单、支付与消息通知。一个操作背后涉及业务处理、渠道接入和终端反馈，任何一段出现异常，都可能让业务人员难以判断下一步。设计重点是理清模块职责，并为跨环节协作保留明确的处理边界。

核心链路简化示意

以下图示为技术思路的简化表达。

  1. 01 / 业务入口订单与门店操作
  2. 02 / 订单服务组织核心业务流程
  3. 03 / 支付接入对接支付网关
  4. 04 / 终端通知长连接、推送与反馈

架构取舍与实现

01

以业务职责组织模块

难点订单、支付与风控彼此关联，混在一起会放大修改和联调的影响。

方案以订单模块组织核心业务，承担支付网关开发，并与风控模块协作，分别处理业务流程与外部渠道接入。

价值让需求变更能够落到具体职责，便于定位影响范围、协调开发和安排验收。

02

把通知链路作为独立问题处理

难点订单处理完成，并不等于门店或服务员已经收到通知。

方案系统通过 RabbitMQ 消费新订单通知，采用 Netty 长连接优先、极光 Push 兜底，串联门店打印与服务员推送。

价值将业务处理与终端触达分层考虑，既能发挥长连接的即时性，也保留另一条通知路径。

03

围绕回执做有限补偿

难点网络变化和终端状态会造成未确认通知，多节点重推又可能带来重复。

方案通知链路结合应用回执对未确认订单有限重推，并利用 Redis 计数限制多个节点重复发起极光通知。

价值把补偿范围和重复控制落到具体机制，同时保留服务端处理与终端实际完成之间的区别。

工程价值

把订单、支付与通知各自的复杂度放在明确边界内，为持续迭代和异常定位提供结构基础。

验证关注点

  • 订单处理成功与终端收到通知，是否有清晰的状态区分？
  • 终端断连或回执缺失时，补偿次数和停止条件是否明确？
  • 多个节点同时处理通知时，重复推送是否得到控制？

我的职责

负责云小二、云掌柜的架构搭建与核心开发，主导订单模块，承担支付网关开发并参与风控模块。

技术与主题

  • 业务架构
  • 订单 / 支付
  • RabbitMQ
  • Netty
  • Redis
  • 极光 Push
